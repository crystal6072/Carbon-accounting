## 1. 前置问题

### 1.1 组织架构与租户的关系

**结论：一个租户有且只有一棵组织树，树根为系统随租户创建自动生成的根组织（名称 = 租户名称），不可删除、不可移动、不可再建同级；其余组织一律挂在根组织或其下级之下。**

| 项 | 原型口径 |
| :--- | :--- |
| 根组织 | **开户时创建**（租户管理 PRD V0.13 §4.1-25）：平台创建租户后立即建 1 个根组织，名称取租户名，类型取该租户类型预置字典首项（企业→集团、政府→委办局、机构→总部、园区→园区），`isRoot = true`。原型 `ensureTenantRootOrg(tenantId, tenantName, tenantType)` 保留为**幂等兜底**（重试、补建、数据修复场景），不再作为唯一创建时机 |
| 唯一性 | `getRootOrg` 取本租户唯一根；页面文案「租户内只有一个根组织」「不可再建同级」 |
| 不可删除 / 移动 | 根节点的「删除」「移动」按钮禁用，提示「根组织由系统自动创建，不可删除 / 不可移动，组织名称可改」 |
| 树结构 | 全部节点 `orgId = tenant_id` 隔离，每租户一棵树；`path` 形如 `/ON001/ON002/` |

判断依据：

1. `mock/org.ts` 的 `ensureTenantRootOrg` 与 `getRootOrg` 均基于「每租户一个根」实现，种子数据每租户只 seed 一个 `isRoot` 节点。
2. `TenantOrgPage.tsx` 移动逻辑注释「租户内只有一个根组织，故无『作为根节点』选项」；`OrgNodeModal` 不再支持新建顶级节点（parentId 必填）。
3. 页面 `org-panel-tip` 文案明确「层级上限 5 层；同一上级下名称不可重复；停用节点不可挂新成员，存量成员数据范围不变」。

推论：

1. 原型**不采用**前向 PRD 的「多根节点（parent_id = 0 并列）」方案，统一收敛为单根。
2. 组织节点数不受 5 层上限之外的硬约束；单租户建议不超 500 节点（前向 PRD D15，原型无强制）。
3. 成员 `dept_id` 语义等于 `org.id`，见 §1.2。

### 1.2 「组织架构」与「部门」的关系

**结论：组织节点与成员管理里的「部门」是同一实体，不做两套表。**

| 项 | 口径 |
| :--- | :--- |
| 成员侧字段 | `TenantMemberItem.deptId`（组织节点 id，可空）、`deptName`（组织名称冗余） |
| 父子对应 | **生产口径：按 `tenant_member.dept_id = org.id` 关联**（V0.2 起，D08）；原型现状按 `deptName === org.name` 名称匹配（见 `TenantOrgPage.memberCounts` / `selectedMembers`），属待改造项 |
| 模块码 | 统一 `org`（orgMeta 注释：「模块码 org，与用户体系 PRD 的『部门』是同一实体」） |

> 原型匹配用「名称相等」，要求组织名称唯一且成员 `deptName` 与组织 `name` 保持一致，**存在改名即失配的硬缺陷**。V0.2 起统一改为以 `dept_id`（= `org.id`）为主关联键（D08，字段清单 T02 已由「建议」升级为「必改」）。触发点：平台侧「组织架构」页签上线后，平台看到的人数是错的会直接质疑数据可信度，因此本项与 §5.10 同批落地，不后置。

### 1.3 组织类型在原型中的形态

**结论：原型没有独立的组织类型字典 CRUD，组织类型只是一段来自预置字典的字符串标签（typeName）。**

| 项 | 原型口径 |
| :--- | :--- |
| 预置字典 | `ORG_TYPE_PRESETS` 按租户类型给默认集：企业=[集团,子公司,工厂,车间,部门]、政府=[委办局,处室,科室]、机构=[总部,分支机构,部门]、园区=[园区,片区,企业,部门] |
| 下拉来源 | `orgTypesOf(tenantId, tenantType)` = 预置集 ∪ 本租户已用类型（去重）；编辑 / 新增时从该下拉选 |
| 存储 | 组织节点直接存 `typeName: string`，**不存** `org_type_id` 外键、不存独立字典表 |
| 停用 / 改名 | 无字典行管理；预置类型即选即用，无「停用类型」概念 |

> 与原前向 PRD §5.6（组织类型字典 CRUD + org_type_dict 表）不同，原型把类型简化为标签。如后续需要「类型停用 / 强约束下级类型」，需补 `org_type_dict` 表与 `org_type_id` 外键（见字段清单 §6 T05、本文 §10 T03）。

## 2. 需求描述

租户管理员在租户端维护本租户的组织树：以开户时自动生成的根组织为起点，新建下级、编辑、移动、启用 / 停用、删除组织节点，并查看各节点的直属成员（只读）；组织类型从预置字典下拉选择。组织树供成员挂靠、角色数据范围与业务数据归属引用，本模块只负责组织维度本身。

平台侧另提供**只读查看**：平台超管在「租户管理 → 租户详情 → 组织架构」页签查看某租户的组织树与组织下成员（见 §5.10）。平台不改组织数据、不代配置，写操作仍只发生在租户端。

## 3. 业务流程

### 3.1 新增下级

```mermaid
flowchart TD
  A[选中节点 或默认根组织] --> B[填名称 类型 编码 选填 负责人 排序]
  B --> C{名称非空 长度 1 至 50}
  C -->|否| D[拒绝 定位到名称]
  C -->|是| E{排序为不小于 0 的整数}
  E -->|否| F[拒绝 定位到排序]
  E -->|是| G{名称同上级下不重复}
  G -->|否| H[拒绝 提示同级重名]
  G -->|是| I{上级为启用状态}
  I -->|否| J[拒绝 提示上级已停用]
  I -->|是| K{新建后层级不超 5 层}
  K -->|否| L[拒绝 提示层级上限 5 层]
  K -->|是| M[生成 code 与 path 置启用]
  M --> N[写审计]
```

### 3.2 编辑

```mermaid
flowchart TD
  A[打开节点 编辑] --> B[改名称 类型 负责人 排序]
  B --> C{名称非空 1 至 50 排序不小于 0}
  C -->|否| D[拒绝]
  C -->|是| E{同上级下不重名 排除自身}
  E -->|否| F[拒绝 提示同级重名]
  E -->|是| G[保存 写审计]
  G --> H[注：编辑不改上级 改上级走移动]
```

### 3.3 移动

```mermaid
flowchart TD
  A[打开节点 移动] --> B[选择新上级]
  B --> C{新上级不是自身或自身子孙}
  C -->|否| D[拒绝 提示不可移动到自身或下级]
  C -->|是| E{新上级为启用状态}
  E -->|否| F[拒绝 提示上级已停用]
  E -->|是| G{移动后层级不超 5 层}
  G -->|否| H[拒绝 提示层级上限 5 层]
  G -->|是| I{目标层级下无同名节点}
  I -->|否| J[拒绝 提示目标层级已存在同名]
  I -->|是| K[重算本节点与全部子孙的 level 与 path]
  K --> L[提示受影响成员数据范围按新树生效 历史业务数据归属不变]
  L --> M[写审计 记移动前后上级]
```

### 3.4 停用与启用

```mermaid
flowchart TD
  A[对启用节点发起停用] --> B{存在启用状态下级}
  B -->|是| C[拒绝 提示先停用下级]
  B -->|否| D[二次确认 展示挂靠成员数]
  D --> E[置停用 写审计]
  E --> F[发起启用]
  F --> G{上级为启用状态或本节点为根}
  G -->|否| H[拒绝 提示先启用上级]
  G -->|是| I[置启用 写审计]
```

### 3.5 删除

```mermaid
flowchart TD
  A[对节点发起删除] --> B{是根组织}
  B -->|是| C[拒绝 提示根组织不可删除 仅名称可改]
  B -->|否| D{有下级节点}
  D -->|是| E[拒绝 提示先处理下级]
  D -->|否| F{有挂靠成员 按名称匹配}
  F -->|是| G[拒绝 提示先调整成员所属组织]
  F -->|否| H[二次确认 删除后不可恢复]
  H --> I[物理删除节点 写审计]
```

## 5. 业务规则

### 5.1 组织树与层级

1. 系统按租户隔离组织树，一个租户一棵树，`orgId`（即 `tenant_id`）贯穿全部节点。
2. 系统确保每租户有且只有一个根组织：`parentId = null`、`isRoot = true`、名称默认 = 租户名称；其余节点一律挂在根或其下级之下。
3. 系统限制节点层级上限为 5 层（原型常量 `ORG_MAX_LEVEL = 5`），第 5 层节点不可再建下级。
4. 系统以 `path` 存储从根到本节点的 ID 路径（形如 `/ON001/ON002/`，含首尾斜杠），用于「含下级」查询与移动校验。
5. 系统以 `level` 存储本节点层级序号（根为 1，逐级加 1）。
6. 系统要求同一上级下组织名称不重复（含根节点之间）。
7. 系统要求组织编码在租户内唯一（大小写不敏感），编码可手填或留空由系统生成（生成后转大写）；创建后可改但保存时判重。
8. 系统按 `sort` 升序排列同级节点；`sort` 为不小于 0 的整数，缺省 1。
9. 组织类型 `typeName` 取本租户可用类型（预置集 ∪ 已用类型），为字符串标签，不约束「该类型下只能挂什么子类型」。

### 5.2 新增下级

1. 操作人选中已有节点（默认根组织）作为上级，点击「新增下级」。
2. 系统校验上级节点处于启用状态；上级为停用时按钮禁用。
3. 操作人填写组织名称（必填）。
4. 操作人选择组织类型（来自类型下拉）。
5. 操作人选填组织编码，不填则系统生成（转大写）。
6. 操作人选填负责人姓名（仅展示，不联动权限）。
7. 操作人填写排序号（默认「同级末位 + 1」，不小于 0）。
8. 系统校验名称非空、长度 1 至 50。
9. 系统校验排序为不小于 0 的整数。
10. 系统校验同一上级下名称不重复。
11. 系统校验组织编码在租户内唯一（不区分大小写）。
12. 系统校验新建后层级不超过 5 层。
13. 系统生成 `path` 与 `level`，置节点为启用状态。
14. 系统写审计，记上级、名称、类型。

### 5.3 编辑

1. 操作人修改组织名称、组织类型、负责人、排序号。
2. 系统校验名称非空且同上级下不重名（排除自身）。
3. 系统校验排序为不小于 0 的整数。
4. 系统校验编码在租户内唯一（排除自身，不区分大小写）。
5. 系统不修改 `parentId`：改上级必须走「移动」操作。
6. 根组织的名称 / 类型 / 负责人 / 排序可改；其余同上。
7. 系统写审计。

### 5.4 移动

1. 操作人发起移动，为目标节点选择新上级（下拉排除自身、自身子孙、停用节点、根组织）。
2. 系统校验新上级不是目标节点自身。
3. 系统校验新上级不是目标节点的子孙节点（以 `path` 前缀判定）。
4. 系统校验新上级处于启用状态。
5. 系统校验移动后目标节点及其子树的最大层级不超过 5 层。
6. 系统校验目标层级下不存在同名节点。
7. 系统在移动成功后重算目标节点与全部子孙节点的 `path` 与 `level`。
8. 系统提示影响：直属成员的数据范围按新树生效，历史业务数据归属不变（原型 `moveConfirm` 文案）。
9. 系统写审计，记移动前后上级与影响。

### 5.5 停用与启用

1. 操作人对启用状态组织发起停用。
2. 系统校验不存在启用状态的下级组织；存在则阻断并提示先停用下级。
3. 系统二次确认并展示挂靠成员数（按名称匹配）。
4. 操作人确认后系统置该节点为停用。
5. 系统禁止向停用节点挂靠新成员（成员管理侧约束）、禁止在其下新建下级。
6. 系统保持存量成员的组织归属不变，其数据范围按原树计算。
7. 操作人对停用状态组织发起启用。
8. 系统校验其上级为启用状态或该节点为根组织；否则阻断并提示先启用上级。
9. 系统置该节点为启用。
10. 系统写审计。

### 5.6 删除

1. 操作人对组织发起删除。
2. 系统校验该节点不是根组织；根组织阻断并提示「根组织由系统自动创建，不可删除，仅可修改组织名称」。
3. 系统校验该节点无下级组织（含已停用节点）。
4. 系统校验该节点无挂靠成员（按 `deptName === org.name` 匹配，含停用成员）。
5. 系统二次确认「删除后不可恢复」。
6. 系统通过全部校验后物理删除节点，写审计，记删除节点的名称、类型、完整路径。
7. 系统不删除任何业务数据；历史业务数据按 `owner_org` 追溯不受影响。

> 原型未实现前向 PRD「被业务数据归属引用」第三道删除拦截（核算项目 / 产品 / 工艺 / 因子 / 活动数据的 `owner_org`），见 §10 T04。

### 5.7 查看直属成员

1. 操作人选中组织节点，右栏展示「直属成员」表（姓名、手机号、角色、成员状态）。
2. 系统按成员 `deptName` 与组织 `name` 相等匹配（见 `TenantOrgPage.selectedMembers`）。
3. 该表只读，成员归属调整在成员管理模块完成。

### 5.8 与其他模块的契约

| 对端 | 契约 | 落点 |
| :--- | :--- | :--- |
| 租户管理 | 模块授权 `org` 决定租户端菜单是否渲染；**根组织由开户动作创建**（租户管理 V0.13 §4.1-25），`ensureTenantRootOrg` 仅幂等兜底 | 租户管理业务 PRD |
| 租户管理 | 平台侧只读查看：租户详情页「组织架构」页签读取 `org` + `tenant_member`，只读、不写审计（导出除外） | 租户管理业务 PRD §4.19、本文 §5.10 |
| 成员管理 | 成员 `dept_id` 即 `org.id`，可空；为空按「仅本人」；组织停用后不可挂新成员，存量不变 | §5.5、成员管理 PRD §4 |
| 角色管理 | 数据范围「本组织及下级 / 本组织」按 `org_path` 实时计算，不使用快照 | 角色管理 PRD |
| 业务数据 | 核算项目、产品、工艺、工序、因子记录 `owner_org_id`；活动数据、检测、报告继承项目归属 | 整体设计方案 §3.4 |
| 审计日志 | 组织新增、编辑、移动、启用 / 停用、删除全部写审计 | §5 |

### 5.9 通用

1. 系统按角色持有校验组织架构功能码。
2. 系统在无功能码时不渲染菜单并拒绝接口。
3. 系统不接收前端传入的 `tenant_id`，一律按当前会话租户取值。
4. 系统对所有写操作写审计。
5. 系统拒绝任何跨租户的组织节点读写。

### 5.10 平台侧只读查看（落租户管理详情页，V0.2）

> 定位：本模块**只提供数据口径与展示契约**，页面归属在《租户管理业务 PRD》V0.13 §4.19。两端规则必须一致，改一处须同时改两处。

1. 入口唯一：租户管理 → 租户详情页 → 「组织架构」页签；**不设独立跨租户「组织架构全景」菜单**（租户管理 D52）。
2. 平台侧对该租户组织树**永久只读**：不可新建、编辑、移动、停用、启用、删除，不提供受控代配置（D-06 仍不纳入）。
3. 系统按 `tenant_id` 隔离加载，一个租户一棵树；根组织唯一（`is_root = 1`、`parent_id = NULL`），由开户时创建（租户管理 §4.1-25）。
4. 根组织缺失时展示异常态「该租户根组织缺失，请核查开户初始化」，只读兜底展示已存在节点，**不自动补建**。
5. 系统返回扁平节点数组由前端拼树，节点含名称、类型、层级、编码、负责人、状态、**直属人数**、**含下级人数**；默认展开根与第一层。
6. 成员口径：默认**直属成员**（`dept_id = org.id`）；可切「含下级」，按 `org_path` 前缀匹配。
7. 成员状态展示沿用成员管理口径：默认「正常」，筛选项「全部 / 正常 / 已禁用」；「已移出」仅在「全部」下可见。
8. 成员表字段：姓名、手机号（中间四位脱敏）、角色、成员状态、加入时间；分页 20 条。
9. 系统展示停用组织（置灰 + 标记）与其直属成员；**停用租户同样可查看**（只读，不属数据冻结范围）。
10. 查看与搜索**不写审计**、不写任何业务数据；**仅导出写平台审计**（租户、节点数、操作人、时间）。
11. 导出仅含组织维度字段，不含成员姓名、手机号与角色。
12. 未授权 `org` 模块的租户：平台侧仍可进页签，但展示空态「该租户尚未开通组织架构模块」，不渲染空树。
13. 本能力**不新增功能码**，受「租户管理」功能码约束；无该功能码时接口拒绝。

## 9. 设计决策

| 编号 | 事项 | 决议 | 落点 |
| :--- | :--- | :--- | :--- |
| D01 | 根组织形态 | 单根：每租户一个系统自动创建的根组织（parentId = null，isRoot 唯一），不可删不可移；前向 PRD 多根方案不在原型落地 | §1.1、§5.1 |
| D02 | 术语与模块码 | 对外统一「组织架构」，模块码 `org`；与「部门」同一实体，成员 `dept_id` = `org.id` | §1.2、§5.8 |
| D03 | 层级上限 | 5 层上限（原型 `ORG_MAX_LEVEL`） | §5.1 |
| D04 | 组织类型 | 原型简化为预置字符串标签 `typeName`，无独立字典表 / 外键；如需字典能力需补表（§10 T03） | §1.3、§5.1 |
| D05 | 移动后的数据影响 | 移动只改树结构与 path/level，不改任何业务数据归属；历史业务数据仍按原路径追溯 | §5.4 |
| D06 | 删除策略 | 物理删除；仅「无下级、无成员」两道拦截止删，无业务引用第三道拦截（见 §10 T04） | §5.6 |
| D07 | 成员匹配 | 原型按 `deptName === org.name` 匹配直属成员；字段清单建议改以 `dept_id` 主键关联（§6 T02） | §1.2、§5.7 |
| D08 | 平台侧能力 | 只读查看**纳入**，落租户管理详情页「组织架构」页签（无独立全景菜单）；受控代配置**仍不纳入**。成员与组织关联同期由名称匹配改为 `dept_id` 关联，作为只读查看的前置 | §1.4 D-05/D-06、§5.10、§1.2 |
| D09 | 根组织创建时机 | 由「租户首次进入懒建」改为「**开户时创建**」（租户管理 V0.13 §4.1-25），`ensureTenantRootOrg` 保留为幂等兜底；理由：平台侧要在租户开通后立即看到组织树，空树与「未开通模块」不可区分 | §1.1、§5.10-3、§5.10-4 |
| D10 | 组织人数口径 | 分「直属人数」（`dept_id = org.id`）与「含下级人数」（`org_path` 前缀匹配）两个口径，均只统计成员状态为正常 / 已禁用的行，已移出不计 | §5.10-5、§5.10-6 |
