- 模块名称：**标准文件**
- 业务归属：后台管理 → 基础库 → 标准文件库（方案 §2.3 A1-3、§4.2.5、§八 P05）
- 模块类型：**基础数据维护（轻量）**；不是业务单据、**无审核流、无版本化**
- 维护形态：列表 + 独立详情页 + 独立新增/编辑页

## ⚠️ 必须先给出结论的设计分歧（不得回避）

### 分歧 1：是否上传「标准文件本体」（Q01）

| 出处 | 表述 |
| :--- | :--- |
| 方案 §2.3 A1-3 | 「**上传**核算标准文件，记录名称、编号、版本、适用范围、生效日期」→ 暗示**有文件本体** |
| 方案 §4.2.5 | 只列元数据（名称、编号、版本、发布机构、适用范围、生效日期），**未提文件本体** |

| 口径 | 取舍 |
| :--- | :--- |
| **A（推荐）** | **元数据 + 可选附件**：标准文件记录元数据；附件（PDF）为**选填、可多个**，由附件管理（§C6）承载 |
| B | **仅元数据**，不存文件本体：完全规避**版权风险**（GB/T 与 ISO 标准文本均受版权保护，内部分发亦受限） |

**请给出结论或标【待确认】并写明推荐口径。** 若采纳 A，需同时明确：附件仅用于内部查阅、不作为对外交付物（版权合规边界）。

### 分歧 2：同一标准的多个版本如何表达（Q02）

同一标准常有多个版本（如 `GB/T 24067-2014` 与 `GB/T 24067-2024`），且新版**替代**旧版。

| 口径 | 结构 | 取舍 |
| :--- | :--- | :--- |
| **A（推荐）** | **一个版本 = 一条记录**；唯一键 = 「标准编号 + 版本」；用「**被替代标准**」字段表达新旧关系（新版 → 指向旧版） | 简单，符合「无版本化」的模块定性；模型绑定的是**具体某一条记录**（即某个版本），快照语义天然成立 |
| B | 一个标准 = 一条记录，版本作为版本化字段 | 需引入版本管理，与本模块「无版本化」的定性冲突；模型绑定时"绑哪个版本"需额外表达 |

**请给出结论或标【待确认】并写明推荐口径。**

### 分歧 3：组织能否自建标准文件（Q03）

| 出处 | 表述 |
| :--- | :--- |
| 方案 §3.3.3 | 标准文件被列为 **`PUBLIC` 系统预置数据**（「所有租户可引用（只读）」，与 environment 因子、行业库、计量单位、阶段基线并列）→ 暗示**仅平台维护** |
| 业务实际 | 企业可能有**企业标准、客户指定的标准、国外客户要求的标准**需要录入 |

请明确：**是否允许组织自建标准文件**（`ORG`，本组织可编辑）？若允许，需在字段的「数据来源」上体现两档。
